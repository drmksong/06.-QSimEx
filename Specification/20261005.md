# Core–Euler 코드 재사용 검토

`src/core`와 `src/euler_campaign`의 기존 구현을 대조해 중복 구현 위험과 다음 단계의 재사용 검토 절차를 기록한다.

## 검토 범위와 기준

2026-10-05 기준으로 `src/core` 및 `src/euler_campaign`의 구현, 선언 stub, 관련 계획 문서를 정적으로 비교했다. 파일을 수정하거나 테스트를 실행하지 않았다. Core 코드가 현재 실행 진입점에서 사용되는지, 폐기 예정인지는 이 검토에서 추정하지 않는다.

Euler 폴더에는 DFN·geometry·model·profile·Q′·simulator·config의 `.py` 구현이 있다. `coverage.pyi`, `euler.pyi`, `campaign.pyi`, `ports.pyi`는 계약 선언이며 대응하는 `.py` 구현은 아직 없다. 따라서 이들 선언을 구현할 때 Core의 기존 동작과 대조해야 한다.

2026-10-05 orchestration 구현 시 기존 재사용 대상을 재검토했다. Core에는 Euler campaign의
typed plan/state checkpoint나 domain ID 기준 coverage-pool 조회 helper가 없어 직접 재사용할
기능이 확인되지 않았다. 따라서 orchestration의 round 전이·paired 비교에는 Euler의
`coverage.py`와 `euler.py`를 사용하고, 실행별 저장은 `CampaignStore` port 뒤에 둔다. Plan의
stable update-rule ID와 fingerprint는 재개 시 다른 규칙으로 바뀌는 것을 막는다. 실제 저장
구현은 별도 단계에서 port의 계획 불변성, SimulationResult deduplication, 누적 pool coverage,
round/state atomicity를 만족해야 한다.

### 다중 시작점·중단 후 재개 요구사항 (2026-10-05)

단일 `CampaignPlan.initial_parent`를 순서 고정된 시작 시그니처 목록과 branch-local lineage
state로 확장한다. 한 lineage의 local saturation은 campaign 종료가 아니라 다음 시작점으로
이동하는 조건이다. 모든 branch의 simulation evidence는 기존 결과를 보존하는 하나의
campaign pool에서 `domain_id`로 deduplicate하되, score pairing과 provenance는 branch별로
분리한다.

현재 `CampaignStore` 계약은 `save_simulation`만 제공하고 signature/seed로 결과를 다시 읽는
API가 없으므로, round 중단 뒤 이미 끝난 simulation을 실제로 재사용할 수 없다. 저장 구현
단계에서 `load_simulation(campaign/execution fingerprint, signature_id, seed)`를 추가하고,
각 완료 simulation을 round checkpoint보다 먼저 지속 저장한다. 재개 시 같은 plan fingerprint의
lineage cursor와 parent를 복원하고, 저장된 results로 round 계산을 재구성해 미완료 simulation만
실행한다. 전체 누적 coverage가 채워지면 종료하며, 모든 시작점 소진 시 남은 gap과 종료 근거를
보존한다. Legacy Core ledger/CSV는 명시적 provenance import 없이는 pool에 섞지 않는다.

## 다음 구현 계획에 적용할 가이드

남은 Euler 구현 항목은 각각 다음 검토를 통과한 뒤에만 구현 계획을 구체화한다. 검토는 재사용을 강제하기 위한 것이 아니라 **기존 기능을 확인하지 않은 채 같은 기능을 새로 쓰는 일을 막기 위한 선행 절차**다.

1. 기능 이름뿐 아니라 입력 단위, 출력 형식, domain/seed semantics, 수치 경계 및 오류 처리를 기준으로 `src/core`와 현재 계획·stub에서 선행 구현을 찾는다.
2. 각 책임을 다음 중 하나로 분류하고 근거를 기록한다.
   - **직접 재사용:** 의미와 계약이 일치한다.
   - **adapter로 재사용:** 핵심 동작은 일치하나 자료형·schema·저장 형식 차이를 명시적으로 변환할 수 있다.
   - **공통 primitive 추출:** 계산식·알고리즘은 같지만 각 모듈의 상위 정책은 달라 작은 순수 기능만 공유한다.
   - **분리 구현:** 계약·정확도·성능·의존성 차이로 기존 구현을 쓰면 동작이 바뀌거나 결합이 과도해진다. 차이와 분리 이유를 적는다.
3. 재사용하지 않기로 했더라도 기존 구현을 무시하지 않는다. 동일 기능이 병존하는 위치, 허용되는 차이, 향후 통합 여부를 로그와 계획에 남긴다.
4. Core의 구형 자료형이나 fallback을 새 Euler 계약에 맞추기 위해 의미를 바꾸지 않는다. 새 경계 adapter나 공통 helper가 필요하면 별도 범위와 검증을 계획한다.
5. 계획 업데이트는 구현 승인과 별개다. 각 단계의 실제 코드 변경은 사용자의 명시적 요청이 있을 때만 시작하고, 테스트 통과 통보만으로 다음 단계를 착수하지 않는다.
