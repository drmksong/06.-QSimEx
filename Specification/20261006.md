# Euler 캠페인 파라미터 탐색 후속 설계 논의

- 날짜: 2026-10-06
- 상태: 탐색 규칙 및 로그 회귀 수정 관련 unittest 통과; 사용자가 campaign을 실행했고 Q′ plateau 관측을 기록함
- 기준 incident: [EulerCampaignSaturationIncident_20261005.md](EulerCampaignSaturationIncident_20261005.md)
- 설계 계약: [DesignSpec_20260922.md](DesignSpec_20260922.md) 5.6.11

## 배경

2026-10-05 실행은 설정된 density·size·orientation 범위를 충분히 탐색하지 않았는데도
`all_lineages_saturated`로 끝났다. 기존 흐름에서는 후보 검증 거부 후 해당 feature를
`blocked_features`에 추가하며, 모든 feature가 막히면 lineage를 소진 처리했다. 사용자는
이 정책을 잘못된 것으로 판단하고 폐기하기로 했다. 거부된 후보를 수락하지 않은 parent로
되돌리는 것은 가능하지만, 거부만으로 해당 feature의 탐색을 영구 차단하지 않는다.

## 합의한 탐색 원칙

1. **Density 주도 탐색**
   - density는 넓은 파라미터 범위를 탐색하는 중심 축이다.
   - density 후보가 거부되면 step cap을 2배로 확대해 다음 후보를 만든다.
   - 확대된 step cap은 후보가 수락된 뒤에도 유지한다.
   - 여러 joint set의 density는 한 후보에서 하나만 바꾸고, set_id 오름차순으로 순환한다.
   - density feature의 첫 non-zero sensitivity 방향을 고정하고, sensitivity가 없거나 0이면
     상한(+) 방향으로 시작한다. 그 방향의 bound에 도달하면 해당 feature를 완료 처리하고
     다음 set으로 진행한다.
   - 밀도 범위가 소진되면 초기 signature를 바꾸어 새 탐색을 시작한다.
   - 현재 계획의 시작 signature를 모두 소진해도 coverage가 미완료이면 자동 생성이나
     `all_lineages_saturated` 대신 `decision_required`로 멈춰 새 start signature를 요청한다.
   - signature-space 탐색은 density를 중심으로 하며, size 등 나머지 feature에는 물리적·계획상
     제약을 만족하는 한 일정한 무작위성을 허용한다.
   - 새 signature 생성·선택 방법, 여러 joint set density의 탐색 순서 및 step 초기화는 미정이다.

2. **크기와 density의 분리 제안**
   - density와 size를 한 후보에서 동시에 변경하지 않고 번갈아 탐색한다.
   - 이는 두 값의 실제 상호작용을 부정하는 것이 아니라 제안 변화의 효과를 분리해 관측하기
     위한 것이다.
   - density type이 P32인 경우 설정 P32를 유지한다. size 분포가 변하면 생성기의 계약에 따라
     기대 joint count가 달라지지만, 절리 개수는 탐색변수·합격 기준·별도 평가 지표로 사용하지
     않는다. 절리망 재현의 핵심 입력은 밀도·크기·방향이며, 생성된 절리 개수는 이 입력 및
     생성기의 확률적 구현에서 따라오는 부수 결과로 본다. 설정 P32는 목표값이며 유한한 Poisson
     생성 DFN의 realized P32는 변동할 수 있다.

3. **Orientation sweep**
   - `orientation_beta`를 0°–90° 구간에서 10°씩 변경한다.
   - 0° 또는 90°에 도달하면 방향을 반전한다.
   - 첫 이동은 현재 signed sensitivity 방향을 사용하고, sensitivity가 없거나 0이면 +10°로
     시작한다. 현재 시작각을 유지한 채 간격을 적용하므로 10° 격자에 재정렬하지 않는다.

4. **Size sampling**
   - 지원하는 반경 범위는 0.05–100m이며 이에 해당하는 직경 범위는 0.1–200m이다.
   - 각 후보는 `size_r_min < size_r_max`를 만족한다.
   - 각 feature의 계획 bound와 반경 구간 0.05–100m의 교집합에서
     `size_r_min`과 `size_r_max`를 각각 로그 균등 추출한 뒤
     `size_r_min < size_r_max`인 pair만 사용한다.
   - 한 size 후보에서 모든 joint set의 pair를 각각 추출해 함께 변경한다.
   - lineage가 활성인 동안 size 후보를 무작위로 계속 생성한다. 각 생성은 모든 joint set의 pair를
     포함한다. 중복 pair도 별도 후보로 처리하며 중복 제거 또는 중복 여부 판정은 하지 않는다.
   - draw seed는 campaign의 exploration seed, lineage 시작 signature, draw index로부터
     결정하며 draw count를 checkpoint에 저장해 재현 가능해야 한다.
   - 연속 영역의 seeded sample을 전 영역 완료로 표시하지 않는다.

5. **종료와 예산**
   - 기존 `coverage_complete` 기준은 primary grid의 모든 bin 관측으로 유지한다.
   - size 범위는 소진 상태가 되지 않으며, size 후보 생성에 횟수 제한을 두지 않는다.
     coverage·예산 등 campaign 종료 조건까지 density/orientation 탐색과 함께 계속 제안한다.
   - coverage 완료와 표본 예산 종료는 별개의 결과다. 예산 종료를 saturation 또는 전 영역 완료로
     표시하지 않는다.

## 구현 범위와 영향

구현 시 `blocked_features` 중심의 단순 종료 정책을 탐색 cursor 기반 상태로 바꾸어야 한다.
거부된 후보·이유, density step 및 탐색 방향, orientation cursor·방향, size draw 진행 상태와
draw count를 checkpoint에 보존해야 중단 후 재개가 결정적이다.
상태 저장·재개, 상태 검증, run summary 및 회귀 테스트를 함께 변경해야 하므로 updater 단독
변경으로 끝나지 않는다.

기존 incident DB와 run generation은 변경하지 않는다. 새 동작의 테스트 및 GPU 시뮬레이션은
사용자가 실행한다. 구현 단계에서 실행이 필요하면 명령만 제공한다.

## 구현 진행 — 1단계

- 기존 normalized-gradient v1/v2 재현 동작은 유지하고, 거부 후 밀도 step 확대를 위한
  별도 stable rule ID `normalized-gradient-density-exploration-v3`를 추가했다.
- 이 rule을 사용하는 campaign에서는 거부된 density candidate의 민감도를 영구 차단하지 않고,
  다음 density 제안의 step scale을 2배로 저장한다. 후보 수락 후에도 확대된 scale을 유지한다.
- lineage checkpoint에 `density_step_scale`을 추가했으며, 이 필드가 없던 기존 serialized
  checkpoint는 기본값 `1.0`으로 읽을 수 있도록 처리했다. CLI 요약에도 scale을 포함한다.
- density rejection 및 step scaling, 구 checkpoint 역직렬화에 대한 테스트를 추가했다.
- 관련 unittest는 사용자가 실행해 통과를 확인했다.
- 이 단계는 density 재시도만 다룬다. orientation sweep, 새 시작
  signature 확장과 최종 budget 종료 정책은 아직 구현되지 않았으며, v3 설정을 실제 campaign
  project에 적용하기 전에 다음 단계를 합의·검증해야 한다.

## 구현 진행 — 2단계

- 정규화 분모에서 현재 좌표의 feasible bounds 바깥 방향으로만 향하는 민감도를 제외했다.
  따라서 bound에 막힌 큰 민감도가 실행 가능한 다른 density 좌표의 최대 step을 축소하지 않는다.
- 모든 비영 민감도가 bound 바깥 방향이면 명시적으로 `bound_limited`와 해당 feature 목록을
  반환한다.
- feasible 좌표의 step 보존과 전부 bound-limited인 경우를 검증하는 unittest를 추가했다.
- Pylance 진단에서 수정한 updater와 테스트 파일의 오류는 발견되지 않았다. 관련
  `unittest` 실행 성공을 사용자가 확인했다.

## 구현 진행 — 3단계

- v3 density exploration rule에 방향별 10° orientation cursor를 추가했다. 첫 이동 방향은
  현재 signed sensitivity를 따르고, sensitivity가 없거나 0이면 +10°를 사용한다. 0°/90°
  경계에서는 후보를 범위에 맞추고 다음 이동 방향을 반전한다.
- 후보가 검증에서 거부돼도 orientation cursor는 시도한 위치까지 진행하며 parent는 유지한다.
  cursor와 방향은 lineage checkpoint 및 run summary에 보존한다. 구 checkpoint 역직렬화는
  새 필드의 기본값을 사용한다.
- sensitivity 방향, unavailable sensitivity의 +10° 시작, 상한 반전, 거부된 후보 이후 cursor
  저장을 검증하는 unittest를 추가했다. 사용자가 아래 명령으로 실행해 통과를 확인했다:
  `python -m unittest src.test.test_campaign src.test.test_euler`

## 구현 진행 — 4단계

- v3 size block은 gradient 제안을 사용하지 않고, 모든 joint set의 size pair를 한 후보에서 함께
  변경한다. 각 반경은 계획 bound와 0.05–100m의 교집합에서 로그 균등 추출하며
  `size_r_min < size_r_max`가 될 때까지 rejection sampling한다.
- seed는 exploration seed, lineage 시작 signature, lineage별 draw count로부터 결정한다.
  `size_sample_count`를 checkpoint와 CLI summary에 저장하며, 구 state에서는 0으로 읽는다.
- 최초 구현은 lineage별 100회 size quota를 뒀으나, 후속 결정에 따라 이를 제거했다. size 범위는
  소진 처리하지 않고 lineage가 활성인 동안 seeded 무작위 후보를 계속 생성한다.
  `size_sample_count`와 seed 파생은 checkpoint에 남겨 재현성을 유지한다. 중복은 검사·제거하지 않는다.
- updater의 재현성·bound·다중 joint set 테스트와 campaign의 후보·카운터 unittest를
  추가했다. 사용자가 다음 명령으로 실행해 통과를 확인했다:
  `python -m unittest src.test.test_campaign src.test.test_euler`
- 100회 제한 제거 후 같은 unittest 명령을 사용자가 다시 실행해 통과를 확인했다.

## 구현 진행 — 5단계 (완료)

- v3 density 제안은 한 번에 joint set 하나만 바꾸고, set_id 오름차순에서 아직 완료되지 않은
  첫 density feature를 탐색한다. 각 feature는 첫 non-zero sensitivity 방향을 cursor에 고정하고,
  sensitivity가 없거나 0이면 상한 방향으로 진행한다.
- bound에 도달하는 후보를 평가한 뒤 해당 feature를 완료 처리한다. rejection도 이미 경계 후보를
  평가한 시도이므로 cursor는 유지되고, 다음 set으로 진행한다.
- lineage별 density cursor/direction/exhausted 정보를 checkpoint 및 CLI summary에 추가했다.
  모든 density feature가 완료되면 lineage를 다음 계획 start로 넘긴다. 모든 계획된 start가
  완료되어도 coverage가 미완료이면 `all_lineages_saturated` 대신 `decision_required`가 되며,
  사용자가 새 start를 추가하면 append-only revision으로 재개할 수 있다.
- density 방향·단일 set 갱신·범위 도달, 전체 start 소진 후 decision-required 및 새 start 확장
  unittest를 추가했다. 사용자가 아래 명령으로 실행해 통과를 확인했다:
  `python -m unittest src.test.test_campaign src.test.test_euler`

## 구현 전에 추가로 합의할 사항

현재 남은 설계 미결 항목은 없다. 아래 추가 결정에 따라 초기 signature 크기 재생성과
지원 반경 범위 변경을 구현하고 관련 unittest를 사용자 확인 대기 중이다.

## 추가 설계 결정 — orientation 탐색 종료

- orientation 범위 자체를 소진 처리하거나 별도 횟수 제한을 두지 않는다. 각 lineage가 활성인
  동안 10° cursor를 양 경계 사이에서 계속 왕복하며, 거부된 후보도 시도 위치로 간주해 cursor를
  진행한다. campaign 종료는 기존 campaign 종료 조건으로 결정한다.
- 이 결정은 현재 구현 동작과 일치하므로 추가 코드 변경은 하지 않았다.

## 추가 설계 결정 — 절리 개수의 취급

- 절리 개수는 중요 탐색변수나 독립적인 합격·score 지표가 아니다. 절리망은 밀도·크기·방향
  입력으로 재현 가능하다는 전제를 두며, 크기 변경에 따라 생성기가 조정하는 기대 절리 개수는
  입력 파라미터의 부수 결과로 취급한다.
- 따라서 앞서 남겨 둔 profile score에서 밀도–크기 상호작용을 별도 개수 지표로 평가할지에 대한
  미결 사항은 해소됐다. profile score/coverage는 기존 기준으로 평가하며, 절리 개수를 별도 목표로
  삼지 않는다.

## 추가 설계 결정 — 범위 밖 초기 크기 재생성

- v3 시작 signature의 size pair가 물리 지원 범위 또는 계획상 feature bounds를 벗어나면, 그
  joint set의 `size_r_min`/`size_r_max` pair만 해당 계획 bound와 0.05–100m 반경 범위의 교집합에서
  seeded log-uniform 방식으로 다시 생성한다. density, orientation 및 다른 joint set의 값은 유지한다.
- 시작 signature의 원본 ID는 lineage 식별자로 보존하고, 재생성된 size를 포함한 signature를
  lineage의 초기 parent로 사용한다. seed는 exploration seed와 원본 start signature ID에서
  결정해 초기화와 재개에서 결정적이다.
- 반경 범위 확장은 직경 기준 0.1–200m에 해당한다.
- 범위 밖 초기 크기 재생성 및 100m 반경까지의 size 탐색을 확인하는 unittest를 추가했다.
  사용자가 `python -m unittest src.test.test_campaign src.test.test_euler` 실행 통과를 확인했다.

## Campaign plan revision 3 준비 완료

- revision 1의 `highq_euler_multistart_campaign_gap_v2.yaml`은 수정하지 않고 보존했다.
- 사용자가 revision 2를 건너뛰도록 요청해 동일 campaign ID의 revision 3을
  `cases/euler/highq_euler_multistart_campaign_gap_v3.yaml`로 준비했다.
- revision 3은 `normalized-gradient-density-exploration-v3`를 사용한다. revision 1의 시작점,
  bounds, seeds, coverage grid, backend 및 execution policy를 유지한다.
- 사용자는 `--force-from-scratch`가 해당 campaign ID의 revision/generation DB와 run output을
  모두 삭제한 뒤 현재 YAML을 독립 root로 실행하도록 요청했다. 이에 revision 3 YAML은 parent가
  없는 root plan으로 설정했다. force 시 새 run-generation ID는 자동 발급된다.
- 다른 campaign의 저장소·출력, source/config YAML은 삭제하지 않는다. v2 YAML 자체도 수정하지 않는다.
- force 정리 동작과 root revision 처리를 구현했다. 사용자가 `--force-from-scratch`로 campaign
  실행을 시작해 실행 로그를 공유했으며, 관련 unittest 전체 실행 결과는 별도 확인되지 않았다.

  `e19d1b91a4ff...`와 `504360dd24a2...`로 다르며 domain ID도 각각

  포함되지 않아 그 상태는 미확인이다.

### 현재 근거로 가능한 설명과 미확정 사실

- 실행 설정의 `Jn=3`. category 설정상 set 2는 `Jr/Ja=1.5/3=0.5`, set 3은
  `Jr/Ja=2/4=0.5`이며, set 1은 `Jr/Ja=3/2=1.5`이다.
- Q′ 계산은 교차 절리가 있을 때 calculation RQD를 최소 10으로 올린 뒤
  `Q′=(calculation RQD/Jn)×(Jr/Ja)`를 적용한다. 따라서 원시 RQD가 10 이하이고
  선택된 최약 절리가 set 2 또는 3 조건이면 `Q′=(10/3)×0.5=1.666666…`으로 고정된다.
  값의 일치는 현재 설정·계산 규칙으로 설명될 수 있다.
- 로그만으로는 각 구간이 실제로 이 경로를 탔는지 확정할 수 없다. 원시 RQD,
  calculation RQD, 선택된 절리 ID 및 Jr/Ja가 기록되지 않았기 때문이다. 특히 각
  구간의 상세 provenance를 검사하기 전에는 plateau 원인을 확정하지 않는다.
- 서로 다른 signature ID는 입력 signature가 달랐음을 나타내지만, seed가 같을 때
  생성 DFN의 변화가 각 프로파일의 최약 교차 절리를 바꾸었는지는 이 요약 로그로
  판별할 수 없다.

### 다음 분석을 위한 기록

- Q′ 계산 규칙이나 사용자 승인 모델 가정을 변경하지 않는다.
- 원인 확정 시 borehole/face 각 profile interval의 `raw_rqd`, `calculation_rqd`,
  `jn`, `jr`, `ja`, `value`, `provenance.source`, `selected_joint_id`를 확인한다.
  진단 로깅을 추가할 경우 기존 요약을 대체하기 전에 구간 단위 데이터가 필요한지
  사용자와 협의한다. 모든 95개 구간을 무조건 출력하는 동작은 아직 결정하지 않았다.
- 다음 실행 로그 또는 저장 결과를 받아 plateau가 실제로 RQD 하한에 의해 생겼는지,
  선택 절리 조건이 반복되는지 확인한 뒤 필요한 변경 범위를 결정한다.

컷오프 산정은 이번 탐색 종료 문제와 분리해 후속 작업으로 남긴다.
